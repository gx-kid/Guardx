01

Defense-in-Depth Cryptography

Relying on a single layer of security (such as HTTPS alone) is insufficient for sensitive family telemetry. GX Parent Control applies independent cryptographic protection at both the payload layer and the transport layer, ensuring data remains protected before, during, and after transit.

Client-Side AES-256-GCM

Sensitive activity records—including messages, notifications, and keystroke events—are encrypted locally on the child device before serialization or transmission.

  • • Algorithm: AES/GCM/NoPadding (256-bit)
  • • IV: Unique 12-byte SecureRandom per item
  • • Integrity: 128-bit GCM authentication tag

Encrypted Transport & Media

Encrypted payloads travel inside TLS tunnels, while real-time audio, camera, and screen streams bypass REST storage entirely via WebRTC.

  • • REST APIs: HTTPS (TLS)
  • • Real-Time Control: MQTTS (TLS)
  • • Live Streams: WebRTC DTLS + SRTP
Why GCM instead of basic CBC? AES-GCM is an authenticated cipher. If even a single bit of ciphertext is modified in transit or storage, decryption automatically fails rather than silently producing corrupted output.
02

Ephemeral Relay Architecture (No Permanent Log Warehouse)

Many monitoring apps dump every SMS, call log, and notification into a permanent third-party cloud database where years of family history accumulate indefinitely. GX Parent Control uses an ephemeral relay queue instead.

Data Delivery & Auto-Purge Lifecycle
1. Child Device
Encrypts payload locally with AES-256-GCM
2. Relay Queue
Holds encrypted batch temporarily in transit
3. Parent Device
Authenticates, fetches & decrypts locally
4. Auto-Purged
Deleted from relay immediately after delivery

Why use a private relay database instead of storing logs in public BaaS tables?

Public Backend-as-a-Service (BaaS) real-time databases are optimized for persistent state, not high-frequency ephemeral queuing, and often retain backups across multi-tenant cloud infrastructure. By operating a dedicated private relay queue with immediate read-and-delete semantics, GX Parent Control minimizes data residency, eliminates third-party log retention, and keeps historical data strictly on the parent's own device.

03

Server-Assisted Key Provisioning: The Engineering Trade-Off

When a child device enrolls, it generates a fresh, cryptographically random 256-bit (32-byte) AES key. How that key reaches the parent device is one of the most important architectural decisions in any monitoring platform.

Why Not Manual Key Entry?

If parents had to manually copy a 64-character hexadecimal key—or re-scan a physical QR code every time they reinstall the app, clear cache, or switch phones—any lost key would permanently lock the parent out of their child's safety monitoring with no recovery path.

How GX Solves It Safely

GX uses an Authenticated Key Provisioning Broker. The key is transmitted over HTTPS (TLS), immediately wrapped at rest on the server using AES-256-GCM envelope encryption, and released only to a JWT-authenticated parent who claims the valid pairing code.

Step-by-Step Pairing Security

  1. Device Enrollment: The child device generates a random 256-bit AES key and a high-entropy bootstrap token, registering over HTTPS.
  2. Envelope Encryption at Rest: The provisioning server never stores the raw key or device credentials in plaintext; both are sealed with server-side AES-256-GCM before writing to disk.
  3. Authenticated Claim: To retrieve the key, the parent must present a valid Supabase JWT session token alongside the pairing code, protected by strict per-IP and per-account rate limits.
  4. Broker Credential Isolation: Once paired, both devices receive unique, role-scoped MQTTS credentials restricted to their specific pairing relationship.

APK Hardening & The Reality of Decompilation

Every Android APK—whether it is a banking app, a messaging app, or a system utility—is a ZIP archive containing compiled Dalvik bytecode (.dex). Anyone can open any APK with tools like jadx or apktool. Static decompilation is a normal property of Android, not a security flaw.

R8 & Selective String Protection

Both apps run full R8 shrinking, aggressive overloading, package flattening, and debug-info stripping. The child service additionally applies compile-time string encryption (StringFog) and asset encryption (AES/CBC/PKCS5Padding), while the parent UI prioritizes Jetpack Compose & Play Integrity/Billing bytecode stability alongside R8.

Zero Master Secrets in APK

API signing secrets, subscription validation, and authorization rules live strictly on the backend. Decompiling the APK yields zero administrative credentials.

Selective Reflection Rules

Specific serialization models and JNI bridges retain predictable signatures intentionally so WebRTC, Firebase, and background services never crash across OEM Android builds.

05

Certificate Trust & Channel Separation

Why System CA Validation Instead of Rigid Leaf-Certificate Pinning?

Modern TLS infrastructure uses automated 90-day certificate renewals (such as Let's Encrypt). Hardcoding leaf or intermediate certificate hashes inside a mobile binary is a common cause of sudden, fleet-wide app outages when certificates rotate or when users are behind legitimate carrier gateways. GX Parent Control enforces TLS validation against Android's System-Trusted Certificate Authorities, guaranteeing continuous child-safety connectivity alongside standard server identity verification.

Separation of Control Pings & Encrypted Payloads

The child application strictly enforces cleartextTrafficPermitted="false" across all network connections. On the parent application, all sensitive data, telemetry, pairing, and authentication calls run exclusively over HTTPS (TLS) and MQTTS; a narrowly scoped fallback channel is reserved solely for lightweight FCM push-wakeup pings (which carry zero user messages, keylogs, or encryption keys) to minimize TLS handshake latency during urgent device wakeups.

06

Strict Tenant Isolation & Access Control

  • Per-Device Broker ACLs: Every child device and parent account is provisioned with isolated broker roles. A device cannot publish to or subscribe to another family's topics.
  • JWT-Verified Operations: Claiming a pairing code, fetching credentials, or unpairing a device requires a valid, server-verified authentication token.
  • Instant Revocation on Unpair: Unpairing immediately updates the server-side access list and revokes broker permissions for that parent-child link.
